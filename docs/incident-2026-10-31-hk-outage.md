## 处置动作清单

- 443 SNI 分流上线（代理与面板共用 443，伪装最佳）
- SSH 加固（root 禁登录/禁密码）+ tcp_fastopen=3
- 2053 备用入站 clients 修复（reality_manager 泛化为填充所有 vless 入站）
- watchdog v2.2：node1/node3/2053 三口每小时探测 + 恢复自动记录
- 域名路由优化器：直连/代理自动择优（5 次中位、20% 容差）+ 用户钉死 + 账本
- 全量链接验证：16 用户 × 2 入口 = 32/32 通过（两次独立实测）

## 经验教训

1. **备用口必须独立**——2053 不经过 nginx，nginx/面板挂了代理仍活。这次它空表 3 天没人发现，就是因为主路径太稳没人碰它。
2. **配置生成器要覆盖全部入站**——\`inbounds[0]\` 硬编码让 2053 空表，修复方式是泛化为"填充所有 vless 入站"。
3. **监控要报"好了"不只报"坏了"**——watchdog v2.2 的恢复探测让香港恢复在 1 小时内被知晓，而不是靠人肉发现。
4. **改 v2rayN 配置必须"停→改→启"**——运行中的 v2rayN 会用内存副本覆盖文件（踩过：绕行列表改动被冲掉）。
5. **测试脚本要防空转**——空循环输出过一次假阳性 "ALL OK"，之后所有批量测试都加数量断言。
6. **应急线与日常线分离**——故障时备用顶上（用户无感），恢复后再回切日常线，切换窗口全程 <10 秒。

## 后记：双实例架构（2026-11-05~06）

REALITY 协议不兼容事件：服务器 xray 26.x 与 Clash 内核(mihomo)不兼容，朋友全部报 REALITY authentication failed。实测兼容矩阵后，采用双实例：

- 443 (xray 26.10.31) → v2rayN 系用户（主线路）
- 2087 (xray 1.8.24) → Clash 用户（legacy 实例，systemd: xray-legacy）
- 配额合并：reality_manager 双 API 查询（10085+10086），两通道流量合并计额
- 配置自动同步：主服务重启/加人时自动重新生成 effective-legacy.json 并重启 legacy
- 监控自愈：watchdog v2.3.1 每小时用 mihomo 探测 2087，失败自动 SSH 重启
- 教训：升级 xray 大版本前必须测 mihomo 兼容性；monitoring probe 必须用与用户一致的客户端核心（xray 26 探测 1.8.24 服务端会误报 DOWN）

全量验证：156 条链接，v2ray 双节点 100%，Clash 2087 通道 100%，Clash 节点1 0%（机场中转机版本问题，预期内）。

### 最终解（2026-11-06 更新）：双实例已撤销，443 换 26.3.27 通用兼容版

进一步定位发现 REALITY 协议断裂点在 26.3.27 → 26.10.31 之间，**26.3.27 与三代客户端全部兼容**（xray 26/1.8、mihomo、sing-box 实测全通）。最终架构：

- 443 主核心 = **xray 26.3.27**（全客户端通用，备份 xray.bak-26.10.31 可回滚）
- 2087 legacy（1.8.24）保留运行（老链接继续有效，作第二通道）
- 配额双通道合并、watchdog v2.4（优雅关闭+双探测）不变

教训修正：不需要双实例也能兼容——选对中间版本即可。排错时本地测试矩阵因"端口残留进程"两次得出错误结论，最终以生产环境实测为准。
